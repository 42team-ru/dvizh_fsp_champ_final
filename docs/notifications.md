# Уведомления: контракт и подключение

Бэкенд сохраняет внутреннюю историю, отправляет Telegram и имитирует MAX/email.
Экраны списка и настроек на сайте пока не подключены. Бот не принимает заявки и не записывает на события:
в сообщении о мероприятии есть ссылка на `/events/{id}`.

## Получатели

| Повод | Кому |
|---|---|
| Напоминания за 24 часа и за час | Разовое: CONFIRMED + организаторы; серия: отметившиеся на дату + организаторы |
| Отмена/перенос даты серии | Отметившиеся на эту дату + организаторы |
| Правка карточки/фото/общего расписания, снятие/удаление, отмена разового | CONFIRMED + PENDING + организаторы |
| Новая запись или заявка, отмена записи | Организаторы |
| Решение по записи, исключение | Затронутый участник |
| Прямой ответ в обсуждении | Автор исходного сообщения |
| Первая анкета организации, повторная после отказа | Активные ADMIN |
| Одобрение/отказ организации | Аккаунт организации |
| Добавление/удаление соорганизатора | Затронутый пользователь; при самостоятельном выходе — автор события |
| Кворум набран/потерян, ручное «Состоится» | Подтверждённые участники разового или отметившиеся на дату серии + организаторы |

Автор действия исключается, системные напоминания приходят и организаторам.
Сохранение без фактических изменений не создаёт уведомление. Обычные сообщения, правки и удаления комментариев
не рассылаются. Потеря кворума не отменяет занятие; после ручного подтверждения колебания численности не рассылаются.
Пересчёт серии объединяет изменения дат и автоматические отмены в одно сообщение на получателя.
Приватные детали, ссылка онлайн-встречи и текст комментария не копируются в уведомления.

## Входящие и long polling

Все пользовательские ручки требуют обычного JWT/cookie и доступны всем ролям только для своего аккаунта.

| Метод | Путь | Результат |
|---|---|---|
| GET | `/api/notifications?cursor=&size=20&unreadOnly=false` | `{items,nextCursor,unreadCount,revision}` |
| GET | `/api/notifications/poll?revision=0&timeoutSeconds=25` | `{changed,revision,unreadCount}` |
| POST | `/api/notifications/{id}/read` | Прочитать своё; повтор безопасен |
| POST | `/api/notifications/read-all` | JSON `{throughRevision: <revision списка>}` |
| GET/PUT | `/api/notifications/settings` | Внешние каналы и категории |
| GET | `/api/notifications/telegram` | `{available,connected,username}` |
| POST | `/api/notifications/telegram/link` | `{url,expiresAt}`; одноразовая ссылка на 10 минут |
| DELETE | `/api/notifications/telegram` | Отключить канал и отменить его очередь |

Уведомление: `id`, `actorId?`, `type`, `category`, `title`, `body`, `targetPath`,
`eventId?`, `occurrenceId?`, `organizationId?`, `createdAt`, `readAt?`, `revision` создания.
Новые сверху; непрозрачный курсор упорядочивает по `(createdAt,id)`. Размер страницы ограничен 1–100.
Список, ревизия и счётчик читаются из одного снимка БД. Чужой id при прочтении — 404.

Алгоритм клиента:

1. Загрузить список и сохранить его `revision`.
2. Запросить `notifications_poll` с этой ревизией. Клиентский timeout должен быть больше 30 секунд.
3. При `changed=true` инвалидировать список и счётчик, перечитать их, продолжить с новой ревизией.
4. При `changed=false` сразу открыть следующее ожидание; это обычный HTTP 200 по истечении срока.
5. При сетевой ошибке повторить с backoff; 401 обрабатывается существующим refresh-перехватчиком.
6. При выходе/смене аккаунта отменить запрос через `AbortSignal` и очистить кэш текущего пользователя.

На одно пользовательское окно достаточно одного ожидания; максимум 10 на аккаунт, 10000 на процесс, далее 429.
Ожидание по умолчанию 25 секунд, максимум 30; 0 означает немедленный ответ.
Ревизия меняется при создании, прочтении и очистке. `read-all` читает только сообщения до переданной ревизии,
поэтому новая запись, пришедшая одновременно с нажатием, останется непрочитанной.
В БД раз в секунду проверяются версии пользователей с активными ожиданиями пакетами до 500;
соединение и транзакция на время ожидания не удерживаются. Несколько реплик не требуют sticky sessions.

## Настройки

PUT полностью заменяет `{channels: [...], categories: [...]}`.
Каналы: `TELEGRAM`, `MAX`, `EMAIL`. Категории: `REMINDERS`, `EVENTS`, `REGISTRATIONS`,
`DISCUSSIONS`, `ORGANIZATIONS`, `ORGANIZERS`.
По умолчанию внешние каналы выключены, категории включены. Подключение Telegram включает этот канал.
MAX/email имеют режим `MOCK` в `availableChannels` и не требуют привязки; реальных отправок нет.

Категории управляют только внешней доставкой: внутренняя история сохраняется всегда.
Исключение — напоминания: существующий `helpers.reminders` в `/api/users/me/preferences`
выключает их во всех каналах. Второго независимого переключателя нет. Без сохранённых предпочтений значение true.
`nearby` и `cheer` пока ничего не рассылают.

Отключение канала/категории отменяет ожидающие доставки. Обратное включение не досылает историю.
Уже начавшийся сетевой запрос отменой настройки отозвать невозможно.

## Telegram и окружение

В Java используется Telegram Bot API; отдельный Python-процесс не требуется.
По умолчанию интеграция выключена и не мешает запуску приложения.

| Переменная | Назначение |
|---|---|
| `TELEGRAM_ENABLED` | `true` для настоящей интеграции; по умолчанию false |
| `TELEGRAM_BOT_TOKEN` | Секрет токена бота |
| `TELEGRAM_BOT_USERNAME` | Имя бота без `@` |
| `TELEGRAM_WEBHOOK_SECRET` | Случайный секрет из A–Z/a–z/0–9/_/-, 1–256 символов |
| `APP_PUBLIC_URL` | Адрес сайта для ссылок; по умолчанию также используется при регистрации webhook; локально http://localhost:5173 |
| `TELEGRAM_WEBHOOK_URL` | Необязательный полный HTTPS URL webhook для скрипта регистрации; позволяет направить туннель прямо на бэк |
| `NOTIFICATIONS_TIME_ZONE` | Пояс разовых событий, по умолчанию Asia/Krasnoyarsk; серии используют собственный пояс |
| `NOTIFICATIONS_SCHEDULING_ENABLED` | Включение фоновой доставки, напоминаний и очистки, по умолчанию true |

На сервере переменные передаются контейнеру `app` из `.env` через Compose.
После запуска настроенного бэкенда один раз зарегистрировать webhook с машины, где есть Node 24:

```bash
node scripts/telegram-webhook.mjs set
node scripts/telegram-webhook.mjs get
# При необходимости отключить получение команд:
node scripts/telegram-webhook.mjs delete
```

Скрипт читает окружение или `.env` текущего каталога. Токен не передаётся аргументом командной строки
и не печатается; секрет скрипта должен совпадать с секретом контейнера.
Регистрация не удаляет накопленные updates. При смене домена повторить `set`.
Скрипт регистрации не вызывается автоматически при старте приложения или CI.
Локально webhook доступен Telegram только через публичный HTTPS-туннель; без него работают внутренние уведомления и заглушки.

### Локальная проверка без входа через туннель

Вход через публичный адрес сайта не требуется: Telegram использует собственный секрет webhook, а ссылку привязки
можно получить после обычного локального входа через браузер или API.

1. Направить HTTPS-туннель прямо на бэкенд: `ngrok http 8080`.
2. Оставить `APP_PUBLIC_URL=http://localhost:5173`, а для регистрации задать полный адрес
   `TELEGRAM_WEBHOOK_URL=https://адрес-туннеля/api/notifications/telegram/webhook`.
3. Запустить бэк с `TELEGRAM_ENABLED=true`, токеном, username и секретом webhook.
   `make back` наследует переменные терминала; корневой `.env` сам не читает. Перед запуском экспортировать его:
   `set -a`, `source .env`, `set +a`.
4. Выполнить `node scripts/telegram-webhook.mjs set` из корня проекта; скрипт сам читает `.env`.
5. Войти на `http://localhost:5173` и в консоли браузера выполнить
   `await (await fetch('/api/notifications/telegram/link', {method: 'POST'})).json()`.
   Открыть полученный `url` в Telegram и нажать Start.

Вместо браузера можно вызвать локальный `POST /api/auth/login`, сохранить cookie и с ним выполнить
`POST /api/notifications/telegram/link`. Полностью анонимной привязки нет: нужно определить аккаунт-получатель.
При локальном `APP_PUBLIC_URL` ссылки из сообщений открываются на компьютере с запущенным фронтом;
`localhost` на телефоне указывает на сам телефон.

Webhook: `POST /api/notifications/telegram/webhook`, защищён заголовком
`X-Telegram-Bot-Api-Secret-Token`. Пользовательский JWT для этого пути не используется.
`update_id` и изменения привязки фиксируются атомарно, повтор update не повторяет действие.
Команды: `/start <token>`, `/status`, `/stop`. Учитываются только личные чаты.
Ссылка хранится в БД хешем, одноразовая; выдача новой отзывает предыдущую.
Один аккаунт сайта и один Telegram могут иметь по одной привязке. Автоматического переноса нет:
сначала `/stop` или отключение на сайте, затем новая привязка.
Блокировка бота и ответ провайдера 403 отключают соответствующую привязку.

## Надёжность и обслуживание

Предметное действие, внутренние сообщения и внешние задания фиксируются одной транзакцией.
`NotificationChanges.watch` сохраняет неизменяемый снимок события до правки под блокировкой его строки;
перед commit сравнивает итоговое состояние после пересчётов серии и собирает единый пакет уведомлений.
Для самостоятельных поводов, например ответа или решения организации, используется `NotificationSubjects`.
Новый повод добавляется как `NotificationType`/факт, новый канал — реализацией `NotificationTransport`.

Доставка хранится в БД: `PENDING → PROCESSING → SENT/MOCKED/SKIPPED/DEAD`.
Claim действует 60 секунд, fenced UUID не даёт старому обработчику перезаписать новую попытку.
Сетевой вызов выполняется вне транзакции с timeout 10 секунд. Перезапуск возвращает просроченный lease в работу.
Backoff начинается с 5 секунд и ограничен 30 минутами, есть jitter; `retry_after` Telegram учитывается.
Доставка старше суток завершается DEAD. При неоднозначном результате HTTP допустим редкий дубль в Telegram.
Глобальный лимит — 20 сообщений/секунду, на чат — одно/секунду; резервирование действует между репликами.
Перед отправкой перепроверяются настройки, версия привязки, а для напоминаний — дата, статус и участие.

Напоминания планируются по занятиям на будущие сроки за 1440 и 60 минут.
При позднем вступлении пропущенные сроки не догоняются. Обработчик запускается каждые 30 секунд;
допустимое опоздание — 5 минут, после начала отправки нет. Перенос инвалидирует старые задания.
На старте планируются только будущие сроки существующих занятий; старые предметные действия не восстанавливаются.
История и завершённые задания хранятся 30 дней, очистка ежедневно в 03:00 UTC.
Параметры доступны в `app.notifications` конфигурации.

Метрики Micrometer: `notifications.queue.size{status}`, `notifications.queue.oldest.seconds`,
`notifications.delivery.errors{channel}`, `notifications.delivery.completed{channel,status}`,
`notifications.reminders.skipped`. Доступ к метрикам определяется существующей конфигурацией Actuator.
Содержимое сообщений, одноразовые ссылки, секрет webhook и токен бота в диагностике доставки не печатаются.

Проверки: `cd backend && ./gradlew test` и `./gradlew postgresTest`.
Telegram проверяется локальным HTTP-сервером, реальные сообщения и секреты для тестов не нужны.
