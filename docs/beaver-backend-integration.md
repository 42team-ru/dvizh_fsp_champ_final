# Бобр в профиле: инструкция для бэкенда

Статус: фронтенд маскота готов; сохранение в БД и описанные ниже эндпоинты **ещё не реализованы**. Это предлагаемый контракт для агента, который делает бэкенд. В этой задаче меняются только документация и фронтенд, реализация сервера остаётся за ним.

## Что уже работает

`/pet` позволяет выбрать настроение, одежду, головной убор, очки, вещь на шее, нижнюю экипировку и инвентарь. Компонент `BeaverPet` получает `mood`, `activity`, `outfit`. Пока страница хранит выбор только в URL: запросов загрузки/сохранения профиля на ней нет.

Источники истины для существующих значений:

- `frontend/src/widgets/beaver-pet/ui/beaver-pet.tsx`: `BeaverMood`, пропсы компонента.
- `frontend/src/widgets/beaver-pet/ui/beaver-wardrobe.ts`: `BeaverOutfit`, идентификаторы предметов, `BeaverActivity` и сборка SVG.
- `frontend/src/widgets/beaver-pet/ui/beaver-clubs.ts`: футбольные клубы и «Хищные бобры».
- `frontend/src/widgets/beaver-pet/ui/beaver-hockey-clubs.ts`: отдельные хоккейные клубы.
- `frontend/src/pages/pet/ui/pet-page.tsx`: готовые образы и подписи вариантов.

SVG, цвета и анимации уже лежат на фронтенде. Сервер сохраняет только идентификаторы из каталога, а не SVG, URL картинки или параметры анимации.

## Формат настроек

```json
{
  "mood": "happy",
  "activity": "hockey",
  "outfit": {
    "shirt": "hc-sokol",
    "hat": "helmet",
    "bottom": "hockeypants"
  }
}
```

Для нового пользователя, существующего пользователя без сохранённых настроек и полного сброса возвращать:

```json
{"mood":"idle","activity":"none","outfit":{}}
```

`mood`, `activity` и объект `outfit` обязательны в запросе полного сохранения. Внутри `outfit` все пять полей необязательные. Отсутствующее поле означает «не надето». `null` для отдельной вещи допустимо нормализовать в отсутствие поля; в ответе отдавать канонический объект без таких полей. Пустую строку и строку `"none"` как идентификатор одежды отклонять: `none` у одежды существует только в URL конструктора, где фронт удаляет поле перед передачей в `BeaverPet`. Для `activity` значение `"none"` корректно.

Не сохранять русское название образа, индекс кнопки или параметр `look`: это готовые комбинации для удобства UI. Сохранять итоговые значения всех выбранных элементов. Например, смена футболки не должна автоматически удалять наушники или ноутбук.

## Полный список допустимых значений

| Поле | Значения |
|---|---|
| `mood` | `idle`, `happy`, `sad`, `thinking` |
| `activity` | `none`, `juggle`, `dribble`, `lift`, `chess`, `ski`, `hockey`, `esports`, `programming` |
| `outfit.hat` | `cap`, `headband`, `beanie`, `swimcap`, `helmet`, `headphones` |
| `outfit.eyewear` | `sunglasses`, `goggles` |
| `outfit.neck` | `medal`, `whistle` |
| `outfit.bottom` | `swimshorts`, `hockeypants` |
| `outfit.shirt`, обычная одежда | `football`, `running`, `training`, `judo`, `hockey`, `programming` |
| `outfit.shirt`, футбольные клубы | `zenit`, `cska`, `fakel`, `yenisey`, `krasnodar`, `lokomotiv`, `spartak`, `rostov`, `dynamo`, `akron`, `beavers` |
| `outfit.shirt`, хоккейные клубы | `hc-cska`, `hc-metallurg`, `hc-lokomotiv`, `hc-severstal`, `hc-torpedo`, `hc-barys`, `hc-spartak`, `hc-neftekhimik`, `hc-sokol` |

Одинаковые названия футбольного и хоккейного клуба — разные значения. `lokomotiv` означает ФК «Локомотив» Москва, `hc-lokomotiv` — ХК «Локомотив» Ярославль. `cska` и `hc-cska`, `spartak` и `hc-spartak` тоже не взаимозаменяемы. `dynamo` — футбольное «Динамо» Москва. `hockey` — общий объёмный свитер «Хищных бобров». `outfit.shirt = "programming"` — тёмная футболка с логотипом ФСП России; это отдельное поле от `activity = "programming"` (ноутбук с кодом). Готовый образ «Спортивное программирование» включает оба значения.

Значения чувствительны к регистру, уже выпущенные id не переименовывать. Если на сервере используются Java enum, JSON должен содержать именно эти строки, включая дефисы у `hc-*`, а не Java-имена `HC_CSKA`.

## Что означают активности

| ID | Что показывает фронт |
|---|---|
| `none` | Без инвентаря |
| `juggle` | Крупный футбольный мяч прыгает рядом; имя сохранено для совместимости |
| `dribble` | Крупный баскетбольный мяч прыгает рядом |
| `lift` | Гантели в лапах, подъём рук |
| `chess` | Доска и шахматные фигуры рядом |
| `ski` | Лыжи и палки на стойке |
| `hockey` | Шайба скользит вперёд-назад по льду, без клюшки и вертикальных подлётов |
| `esports` | Ноутбук с игровым экраном |
| `programming` | Ноутбук с кодом и результатом `Accepted` |

Элементы независимы: футбольная футболка, наушники и ноутбук с кодом — допустимая комбинация. У шапок и наушников общий `hat`, поэтому одновременно надевается один вариант. Хоккейный свитер включает краги; `hockeypants` включает коньки. Сервер не должен требовать шлем для хоккейной футболки или наушники для ноутбука.

## Предлагаемый API

Все пути под `/api`, JSON DTO records, аутентификация существующим JWT из HttpOnly cookie, `@AuthenticationPrincipal Jwt` разбирается в контроллере. Изменение настроек доступно владельцу аккаунта независимо от роли USER/ORG/ADMIN.

| Метод и путь | Доступ | Результат |
|---|---|---|
| `GET /api/users/me/pet` | Вошедший пользователь, только свои настройки | `200` и канонические настройки; если записи ещё нет, значения по умолчанию |
| `PUT /api/users/me/pet` | Вошедший пользователь, только свои настройки | Полностью заменить конфигурацию, вернуть `200` и сохранённый объект |
| `GET /api/users/{id}/pet` | Вошедший пользователь, чтение внешнего вида другого профиля | `200` и настройки; отсутствующий пользователь — `404`; без email, токенов и прочих данных аккаунта |
| `GET /api/pets/catalog` | Вошедший пользователь | Конечный каталог допустимых id и подписей по категориям |

`PUT` не принимает `userId`, владельца определять исключительно по JWT. Изменять чужой профиль через подстановку id нельзя: записывающего `PUT /api/users/{id}/pet` в этом контракте нет. Без входа все перечисленные пути возвращают `401`. Недопустимые id, типы и пустое тело — `400` с русским `ProblemDetail.detail` (например, «Неизвестная хоккейная форма»). Отклонённый запрос не должен частично менять настройки.

В `MeResponse` для существующего `GET /api/auth/me` добавить поле `pet` с таким же объектом, чтобы профиль можно было загрузить одним запросом. Текущие поля профиля сохранить. Если будет общий ответ публичного профиля, поле `pet` в нём должно иметь тот же формат, без копии правил и отдельной модели настроек.

Каталог можно вернуть в форме:

```json
{
  "moods": [{"id":"idle","label":"Спокойный"}],
  "activities": [{"id":"programming","label":"Ноутбук с кодом"}],
  "outfit": {
    "hat": [{"id":"headphones","label":"Игровые наушники с микрофоном"}],
    "eyewear": [{"id":"goggles","label":"Для плавания"}],
    "neck": [{"id":"medal","label":"Медаль"}],
    "bottom": [{"id":"hockeypants","label":"Хоккейные шорты и коньки"}],
    "shirt": [{"id":"hc-sokol","label":"Хоккейная форма — Сокол (Красноярск)"}]
  }
}
```

Это сокращённый пример структуры; реальный ответ должен содержать **все** значения из таблицы выше. Один серверный каталог должен использоваться и для ответа, и для валидации. Не принимать SVG/HTML/внешние URL и не отдавать их из этого API: изображения берутся только из локального гардероба фронта.

## Хранение и внедрение

Добавить хранение в профиле пользователя или в отдельной таблице с уникальным `user_id` и внешним ключом на `users`. Конкретную JPA-модель выбирает бэкенд-агент. Миграция с новым свободным номером; старые миграции не менять. Пользователи без настроек должны получать дефолт без обязательного массового обновления строк. `PUT` обновляет существующие настройки, повторное сохранение не создаёт дубликатов.

Слои соблюдать по текущей архитектуре репозитория (`rest` → `service` → `repository` и `domain`). Контроллер возвращает DTO, сервис отвечает за транзакцию, владельца и каталог. Сохранять только разрешённые поля конфигурации; остальные поля профиля этим запросом не менять.

После реализации обновить OpenAPI и сгенерированный клиент Orval по инструкции проекта. Изменения во фронтенде для отдельного этапа интеграции:

1. Загрузить настройки профиля с сервера и передать их в `BeaverPet`.
2. Дать пользователю редактировать локальный черновик и явно сохранить его через `PUT`.
3. При ошибке оставить черновик, показать ошибку, не утверждать, что всё сохранено.
4. На другом устройстве/после повторного входа загрузить серверный образ. URL остаётся ссылкой на предпросмотр и сам по себе не должен молча перезаписывать профиль.
5. Для старого клиента или неизвестного нового id сделать безопасный fallback в адаптере ответа: неизвестная вещь снимается, настроение → `idle`, активность → `none`. Не передавать неизвестный id напрямую в `buildSlots`: сейчас он ожидает проверенные значения.

`followCursor`, `className` и `onClick` — параметры отображения/поведения компонента, не настройки гардероба. Координаты, размеры, пружины, положения шайбы и слои инвентаря сервер не настраивает.

## Минимальные тесты бэкенда

Следовать проектным правилам из раздела «Тесты»: `@SpringBootTest` + MockMvc + H2, без моков, пользователь через регистрацию и вход, подробный Javadoc перед каждым тестом. Общие шаги брать из `e2e/support/E2eSupport`.

1. Новый пользователь получает дефолт → сохраняет `hc-sokol`/шлем/коньки/`hockey` → повторно входит → читает тот же образ через свой endpoint, `auth/me` и чтение профиля. Затем заменяет образ на наушники + `programming`, старые элементы снимаются; полный сброс возвращает дефолт.
2. Анонимные чтение и запись дают `401`; два пользователя сохраняют разные образы и не могут изменить настройки друг друга; чтение чужого внешнего вида не раскрывает данные аккаунта; несуществующий пользователь даёт `404`.
3. Все id каталога соответствуют поддерживаемым категориям, включая девять `hc-*` и `programming`. Неизвестные id, вещь из чужой категории и пустой запрос дают `400`, сохранённый образ не повреждается. Комбинация футбольной футболки с ноутбуком и наушниками принимается.

Запустить `./gradlew test`; после изменения сущностей/миграций также `./gradlew postgresTest`. Серверное сохранение и подключение UI будут готовы только после выполнения этих шагов; наличие этой инструкции не означает, что они уже реализованы.
