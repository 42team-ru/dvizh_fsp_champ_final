# AGENTS.md

Инструкции для Codex и других агентов. Основной контекст проекта — в `CLAUDE.md`, прочитай его: продукт, роли, модель данных, бизнес-правила и API описаны там.

- Никаких подписей агентов в коммитах и PR (`Co-Authored-By`, `Generated with ...`). Автор коммита — только пользователь.
- Коммиты и пуши делает пользователь, если явно не попросил иначе.

## Проект в двух словах

Платформа совместных спортивных активностей (кейс Столото). Роли: USER, ORG и ADMIN. Человек или допущенная организация создают событие, другие записываются: при `joinMode = FREE` сразу, при `REQUEST` по заявке с решением организатора. Под событием есть комментарии. Админ допускает организации и снимает события с публикации. Эксперты проверяют шесть сценариев из раздела «Сценарии приёмки» в `CLAUDE.md`, поэтому тесты в первую очередь закрывают их.

## Хуки коммитов

Включаются сами при `yarn install` / сборке Gradle (или `make hooks`); нужен Node. Хуки отклоняют подписи агентов и мат в сообщениях коммитов и добавленном коде; не обходить через `--no-verify`. Отчёт: `node scripts/hygiene.mjs scan`.

## Структура

Бэкенд по слоям `rest / service / repository / entity / dto / config / exception`, зависимости только вниз (см. `docs/architecture.md` и CLAUDE.md). Тесты лежат в `src/test/java/com/hackathon/app/e2e`.

## Тесты (твоя основная задача)

Тесты в этом проекте пишет Codex. Правила (полностью в `CLAUDE.md`, раздел «Тесты»):
- Мало, но осмысленных: на фичу 2–4 теста (сквозной сценарий + ошибки/границы + неочевидные ветки). Не по тесту на метод, без тестов на геттеры и конфиги, **демо-режим (DemoService/DemoController) тестами не покрывать**.
- Основной вид: `@SpringBootTest` + `MockMvc` на H2 (`@ActiveProfiles("h2")`), ничего своего не мокать. Testcontainers только в `PostgresMigrationsTest`.
- **Перед каждым тестом подробный Javadoc** с блоками ФЛОУ / ШАГИ / ПРОВЕРЯЕМ / ПОЧЕМУ ВАЖНО. Образец: `AuthFlowE2ETest`.
- После работы запусти `./gradlew test` (в `backend/`), он должен проходить быстрее ~30 секунд. Менялись сущности или миграции — ещё и `./gradlew postgresTest`.

### План тестов по сценариям

Один класс на сценарий (или пару близких), внутри 2–3 теста. Имена полей и путей сверяй с реальным кодом: таблица в `CLAUDE.md` — план, код — истина.

| Класс | Сценарий | Счастливый путь | Ошибки и границы |
|---|---|---|---|
| `EventCreationE2ETest` | 1 | USER создаёт событие с видом из справочника и с новым видом; другой USER находит его в `GET /api/events` (по `q` и `sportId`) и открывает карточку | новый вид, введённый с другим регистром и лишними пробелами, не создаёт дубль `Sport`; ADMIN не может создать событие (403); ORG в статусе PENDING тоже (403); невалидная форма — 400 |
| `OrganizationApprovalE2ETest` | 2 | ORG заполняет анкету и отправляет; публичная страница отдаёт 404; админ одобряет; ORG создаёт событие, и оно сразу PUBLISHED; USER видит страницу организации и её событие | отказ с причиной: организация видит REJECTED и причину; не-админ на `/api/admin/**` — 403 |
| `RegistrationE2ETest` | 3 и 4 | FREE: запись сразу CONFIRMED, организатор видит человека в участниках. REQUEST: PENDING → организатор принимает → CONFIRMED у обеих сторон; второй человек → отклонение → REJECTED с причиной | организатор не может записаться на своё (409); повторная запись не создаёт дубль; решать заявку может только автор (чужой USER и ADMIN — 403); `privateDetails` скрыты, пока запись не CONFIRMED |
| `CommentsE2ETest` | 5 | не записанный USER задаёт вопрос, организатор отвечает; в списке видно авторство и метку «Организатор» у ответа | без входа — 401 |
| `ModerationE2ETest` | 6 | админ снимает событие с причиной: его нет в `GET /api/events`; прямой `GET /api/events/{id}` отдаёт статус и причину, `viewer.canRegister = false`; уже записанный видит событие в `GET /api/registrations/mine` со статусом события | запись на снятое событие — 409; удалённое ведёт себя так же; не-админ — 403 |

Тест на гонку (параллельные записи на последнее место) пиши только если реализован `capacity`: один тест, N потоков, проверка, что подтверждено ровно `capacity`.

### Подготовка данных в тестах

- Демо-режим в тестах выключен (`DEMO_MODE` по умолчанию `false`), на демо-данные не опираться.
- USER и ORG создаются через API: `POST /api/auth/register` с типом аккаунта, затем `POST /api/auth/login`. Cookie `access_token` из ответа передаётся в следующие запросы, как в `AuthFlowE2ETest`.
- ADMIN через API не создаётся: заведи его в тесте через `AppUserRepository` и `PasswordEncoder` (это подготовка данных, не мок), затем войди через `/api/auth/login`.
- Общие шаги (зарегистрировать и войти, создать админа, создать событие) вынеси в один хелпер в `e2e/support/`, чтобы не копировать их по классам.
- Контекст Spring и H2 общие для тестов: давай пользователям уникальные имена (суффикс), чтобы тесты не мешали друг другу.
- Даты событий — в будущем от текущего момента (`Instant.now().plus(2, DAYS)`). Событие «уже началось» через API не создать: если ветка нужна, подготовь его через репозиторий.

```bash
codex exec --skip-git-repo-check -s workspace-write -C /tmp/sport-img \
  "Generate ONE image with your image generation tool, then save it as ./<slug>.png in the current directory. Do nothing else. Prompt: <СТИЛЬ> Scene: <СЦЕНА>" < /dev/null
```

Одна картинка — около 24 тысяч токенов и 3–5 минут. Дальше конвертация в WebP 640×640 и файл `backend/src/main/resources/sport-images/<slug>.webp`.
